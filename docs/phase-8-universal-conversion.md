# Phase 8 — Universal conversion engine

## Scope

Phase 8 adds a shared, browser-local conversion layer to SmartDocs. It turns a bounded natural-language goal or explicit control selection into a typed conversion intent, checks the available capability path, creates a reviewable conversion plan, runs one deterministic adapter, validates every output, and retains an ephemeral conversion-chain record.

The feature is intentionally universal within a measured boundary rather than claiming every file format. The implemented matrix covers PDF page appearance to JPEG, PNG, and WebP; one or more JPEG, PNG, or WebP images to a PDF; and image-to-image conversion among JPEG, PNG, and WebP where the browser can encode the requested target. Existing PDF mutation, OCR, optimization, AI, and safe-action workflows remain separate and available.

## Shared contracts

`src/domain/conversions/types.ts` is the source of truth for format names, source descriptors, page-selection semantics, quality presets, resolution presets, page geometry, target-size scope, validation policy, plans, outputs, and unified result sets. Every plan is versioned as `phase8-conversion-v1` and declares `processingBoundary: browser-local`.

`src/domain/conversions/capabilities.ts` is a capability registry, not a promise that a browser can encode every format. It lists only supported combinations and their limits. WebP encoding is still verified at runtime because browser canvas support varies. The planner rejects mixed PDF/image collections, unsupported target combinations, invalid page selections, excessive pages/files/pixels, contradictory transparency settings, and page-size/orientation conflicts.

## Intent and planning

The existing deterministic intent parser recognizes output formats, `all` or explicit page ranges, quality words, screen/150/200/300 DPI, named page sizes, fit modes, orientation, margins, backgrounds, and decimal KB/MB target phrases. Ambiguous or unsupported language remains visible to the user; it is never silently converted into an invented plan.

Planning applies explicit priorities: source safety and capability checks first, page/file/pixel bounds next, target-size and quality constraints next, and defaults only after the user-visible constraints are represented. Defaults are 150 DPI for PDF rasterization, balanced quality, A4 pages, automatic orientation, contain fit, an 18-point margin, and white background for image collections. The image order in the collection is preserved in the plan and becomes the generated PDF page order.

## Adapters

`src/features/conversion/convert-pdf.ts` reuses the existing PDF.js renderer for PDF-to-image conversion. It renders selected pages sequentially, supports bounded resolution presets, checks cancellation, optionally tries a bounded JPEG/WebP quality search for per-file targets, and validates signatures, MIME, dimensions, and pixel limits.

The same adapter uses pdf-lib for image-to-PDF authoring. Images are embedded as JPEG or PNG; WebP is converted through the browser canvas to a white-background PNG before embedding. Pages are created at A4, A5, Letter, Legal, or an explicit bounded image-size page. Contain, cover, fit-width, and fit-height are supported without stretching. Each page receives the ordered source image, and the generated bytes are reopened through the existing SmartDocs PDF inspection path before success is shown.

`src/features/conversion/convert-image.ts` uses browser canvas for image-to-image conversion. It reports that metadata may be removed, applies an explicit background when JPEG cannot preserve transparency, rejects unsupported WebP encoding, and performs a bounded quality search for per-file targets. No server-side converter or hidden CDN codec is used.

## Validation and failure behavior

`src/domain/conversions/validation.ts` checks magic bytes, MIME agreement, dimensions, total pixels, PDF signature, expected page count, preview/reopen state, target-size state, and measurable size change. Output links are created only after validation. If a target cannot be reached inside the bounded candidate search, SmartDocs reports best effort with measured bytes rather than claiming success. If conversion fails or is cancelled, partial candidates are discarded and the source remains unchanged.

Outputs use deterministic, collision-safe names such as `report-page-002.png` or `image-a.pdf`. Object URLs are revoked when results are replaced or the conversion panel unmounts. Conversion results and the chain history are ephemeral browser state; no database, upload, queue, ZIP dependency, or background service is introduced.

## UI and continuation

The existing PDF core workspace now includes a first-class **Convert** tab. It accepts the active intake image or PDF and also provides local file selectors for a PDF or an ordered multi-image collection. The UI exposes the goal parser, source order, format, pages, quality, resolution, target-size scope, page size, orientation, fit, margin, background, review plan, progress, cancellation, previews, individual downloads, warnings, and optional continuation of a generated PDF through the existing workspace.

The Convert panel is lazy-loaded like the existing OCR, AI, optimization, and safe-action panels. It does not alter source bytes. A generated PDF can be continued into SmartDocs, where the existing recoverable-original behavior applies to the current chain.

## Intentional limits

Phase 8 does not claim DOCX/PPTX/XLSX/HTML editing, universal office round-trips, PDF object-level compression, arbitrary archive creation, searchable-PDF reconstruction during image-to-PDF conversion, ZIP packaging, server queues, cloud conversion, or forensic metadata guarantees. OCR remains an explicit separate step. Those boundaries are shown in the UI and documentation instead of being silently approximated.
