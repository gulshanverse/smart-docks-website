# Phase 9 research notes

## Repository audit

The existing SmartDocs application is a strict React/Vite browser-local workspace with a shared `FileAsset` union currently containing `ImageAsset` and `PdfAsset`. Intake validation is in `src/features/intake/inspect-file.ts`; image limits are 25 MiB and PDF limits are 50 MiB. PDF.js is the inspection/rendering authority and pdf-lib is the authoring authority. The deterministic intent parser is `src/domain/intents/parse-intent.ts`; capability exposure is `src/domain/tools/registry.ts`; workflow steps are `src/domain/workflows/types.ts`; Phase 8 conversion contracts/planning/validation are under `src/domain/conversions/` and adapters under `src/features/conversion/`. The PDF workspace and existing result continuation must remain authoritative for any future validated PDF.

The current model trusts the existing image/PDF category boundary, browser MIME/signature checks, object URL cleanup, and immutable original-file behavior. Phase 9 will extend the union with Office assets rather than create a second application. OOXML inspection will use a bounded ZIP central-directory reader and bounded entry decompression, then DOMParser over selected XML parts. Office binaries will never be sent to the existing AI gateway; only bounded extracted context may be adapted into the existing Phase 6 context boundary.

## Primary-source research

Mammoth.js `1.12.1` is actively maintained and browser-demonstrated, and its repository is BSD-2-Clause. It converts DOCX to semantic HTML and supports headings, lists, tables, images, links, comments, footnotes/endnotes, and common inline styles. Its own documentation emphasizes that DOCX and HTML have a large structural mismatch, that complicated documents are unlikely to convert perfectly, and that it intentionally favors semantic structure over exact styling. Therefore it is suitable for an interpreted DOCX HTML/text preview, not a claim of Word-faithful rendering or DOCX-to-PDF fidelity. Source: [Mammoth repository](https://github.com/mwilliamson/mammoth.js/).

SheetJS Community Edition documents browser parsing through `XLSX.read` with `ArrayBuffer`/`Uint8Array` inputs, while `readFile` is not a browser API. Its parsing options include workbook-only metadata/sheet-name parsing, selected-sheet parsing, row limits, and sparse/dense representations. The documentation states that the codecs focus on raw data, not all features are extracted, and SheetJS Pro is the tier for additional styling, images, graphs, and PivotTables. Therefore Phase 9 can safely use bounded local workbook inspection and cell/text previews, but must not claim faithful Excel rendering or feature-complete PDF export. Source: [SheetJS Reading Files](https://docs.sheetjs.com/docs/api/parse-options/).

PptxGenJS supports browser/React/Vite authoring and emits standards-compliant OOXML, but its documented purpose is generation, not reading or faithful PowerPoint rendering. Using it would add an authoring dependency without solving the required inspection/rendering boundary. Therefore Phase 9 will inspect PPTX package XML directly and expose structural slide/text previews; PPTX-to-PDF remains unavailable unless a separately verified renderer is found. Source: [PptxGenJS repository](https://github.com/gitbrent/PptxGenJS/).

## ZIP/package reader research

`fflate` `0.8.3` is a small, zero-dependency, MIT-licensed pure JavaScript compression/decompression package with browser support and focused inflate/ZIP APIs. Its official repository documents typed-array browser support, ESM builds, ZIP support, and an inflate-only bundle of approximately 3 kB minified. It is suitable for a lazy-loaded bounded OOXML package reader, provided the application enforces central-directory entry counts, compressed/uncompressed byte limits, path safety, supported compression methods, and no external relationship fetching. Sources: [fflate repository](https://github.com/101arrowz/fflate/) and [fflate package documentation](https://www.npmjs.com/package/fflate).

## Decision

Do not add Mammoth, SheetJS, or PptxGenJS to the production bundle merely to imply Office conversion fidelity. Add only the focused `fflate` inflate capability for bounded local OOXML package inspection. The Office layer will not generate PDFs, execute macros, fetch external relationships, or author Office files in this phase.
 Implement the safe, browser-local subset with a small ZIP/package reader and format-specific XML inspection. This avoids CDN dependencies, avoids a large rendering engine, keeps the initial bundle unchanged through lazy loading, and makes the distinction between parsed, structurally understood, previewed, rendered, converted, validated, and preserved explicit. DOCX HTML preview may be offered only as an interpreted preview with warnings. XLSX structural/cell previews may be offered only in bounded ranges. PPTX structural slide previews may be offered only when the required XML parts are present. DOCX/PPTX/XLSX → PDF will be represented as an explicit unavailable capability in this phase because no browser-local faithful renderer was independently verified.
